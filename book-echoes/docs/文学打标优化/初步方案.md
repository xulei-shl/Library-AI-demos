> **兼容旧表 + 新增通用标签体系 + 向量状态解耦 + 推荐历史结构化增强**

这样既能继续使用当前 `literary_tags`，又能支持未来多维度、多版本、多向量空间的文学推荐系统。

---

# 一、总体结论

你当前数据库设计的核心限制是：

```text
books 1:1 literary_tags
每本书只能有一份 tags_json
每本书只有一个 embedding_status
QueryTranslator 只认识 5 个固定字段
```

这适合“单一 5 维阅读体验标签”，但不适合后续扩展：

```text
体裁
主题母题
描述对象
人物关系
叙事风格
时空背景
策展用途
读者场景
```

因此最佳升级方向是：

```text
books
  ├── literary_tags                  旧 5 维标签表，保留兼容
  ├── tag_schemes                    标签方案定义表
  ├── book_tag_results               每本书多方案打标结果
  ├── book_embedding_records         每本书多维度向量状态
  ├── tag_vocabularies               可选：标签词表与别名规范化
  └── literature_recommendation_history 增强推荐历史
```

核心架构从：

```text
一本书 = 一份标签 = 一个向量状态
```

升级为：

```text
一本书 = 多个标签方案结果 = 多个向量画像 = 多路检索融合
```

---

# 二、为什么要这样升级：分步骤判断

## 第一步：识别当前瓶颈

当前 `literary_tags` 有：

```sql
UNIQUE(book_id)
```

这意味着：

```text
一本书只能对应一条打标结果
```

如果你后续想加：

```text
reading_experience
genre_form
theme_motif
literary_entities
narrative_style
geo_temporal
```

只能全部塞进同一个 `tags_json`。

短期可以，长期会有几个问题：

- 某个维度打坏了，需要整本书所有标签一起重跑。
- 词表升级无法记录版本。
- 不同维度无法使用不同 prompt、不同模型、不同置信度阈值。
- 向量状态只有一个 `embedding_status`，无法知道哪个维度已完成向量化。
- 查询转换器和检索器会越来越依赖硬编码字段。

所以要从“单表标签”改成“标签方案化”。

---

## 第二步：区分三种数据

现在 `literary_tags` 同时承担了三件事：

```text
1. LLM 打标结果
2. 向量化状态
3. 推荐检索输入
```

这三者生命周期不同：

| 数据         | 生命周期                                     | 是否应该独立 |
| ------------ | -------------------------------------------- | ------------ |
| LLM 标签结果 | 随 prompt、词表、模型变化                    | 应该独立     |
| 向量化状态   | 随 embedding 模型、拼接策略、collection 变化 | 应该独立     |
| 推荐历史     | 随用户输入和检索策略变化                     | 应该独立     |

所以最佳设计是拆分：

```text
book_tag_results      管 LLM 打标
book_embedding_records 管向量化
recommendation_history 管推荐行为
```

---

## 第三步：保证旧系统不崩

你现在已有大量代码依赖：

```text
literary_tags.tags_json
literary_tags.embedding_status
TagManager.save_tags
db_vectorizer.get_books_to_vectorize
QueryTranslator.VALID_FIELDS
```

所以不能直接废弃 `literary_tags`。

最佳策略是：

```text
Phase 1：保留 literary_tags，作为 reading_experience 旧兼容表
Phase 2：新增 book_tag_results，新的维度全部写入新表
Phase 3：逐步把旧 5 维也迁移到 book_tag_results
Phase 4：literary_tags 只作为兼容视图或历史表
```

---

# 三、推荐的升级后表结构

## 1. 保留 `books` 表不动

原因很明确：

- `books` 是豆瓣模块拥有。
- 文学模块只读。
- 不应让文学推荐系统反向污染元数据采集模块。

建议只增加读取字段，不新增文学专用字段。

如果确实需要增强书目元数据，优先在文学模块建补充表，而不是改 `books`。

例如：

```sql
CREATE TABLE IF NOT EXISTS book_literature_profile (
    book_id INTEGER PRIMARY KEY,
    normalized_title TEXT,
    normalized_author TEXT,
    language TEXT,
    country_region TEXT,
    original_pub_year INTEGER,
    literary_period TEXT,
    is_literary_work INTEGER DEFAULT 1,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

但这不是第一阶段必须做。

---

## 2. 保留并轻微升级 `literary_tags`

当前表不要废弃，建议定位为：

> 旧版 5 维阅读体验标签表，兼容现有打标、导入、导出、向量化代码。

建议增加几列，用于过渡期版本标记：

```sql
ALTER TABLE literary_tags ADD COLUMN tag_schema_version TEXT DEFAULT 'reading_experience_v1';
ALTER TABLE literary_tags ADD COLUMN migrated_to_book_tag_results INTEGER DEFAULT 0;
ALTER TABLE literary_tags ADD COLUMN migrated_at TEXT;
```

升级后完整逻辑：

```text
literary_tags
  - 继续支持旧 5 维标签
  - 继续支持旧 vectorizer
  - 后续可迁移到 book_tag_results
```

不建议继续往 `literary_tags` 里加很多业务字段。

---

## 3. 新增 `tag_schemes`：标签方案表

这张表定义“有哪些打标方案”。

```sql
CREATE TABLE IF NOT EXISTS tag_schemes (
    id INTEGER PRIMARY KEY AUTOINCREMENT,

    scheme_code TEXT NOT NULL UNIQUE,
    scheme_name TEXT NOT NULL,
    scheme_type TEXT DEFAULT 'llm_tagging',

    version TEXT NOT NULL DEFAULT '1.0',
    description TEXT,

    vocabulary_path TEXT,
    prompt_template_path TEXT,
    output_schema_json TEXT,

    is_active INTEGER DEFAULT 1,
    is_filterable INTEGER DEFAULT 1,
    is_vectorizable INTEGER DEFAULT 1,

    default_confidence_threshold REAL DEFAULT 0.65,

    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

推荐第一批写入：

```sql
INSERT INTO tag_schemes
(scheme_code, scheme_name, version, description, vocabulary_path, prompt_template_path)
VALUES
('reading_experience', '阅读体验标签', '1.0', '当前 5 维阅读体验标签', 'config/tag_schemes/reading_experience.yaml', 'prompts/tagging/reading_experience.md'),
('genre_form', '体裁与文体标签', '1.0', '文学体裁、文体、文本形式', 'config/tag_schemes/genre_form.yaml', 'prompts/tagging/genre_form.md'),
('theme_motif', '主题与母题标签', '1.0', '文学主题、母题、核心冲突', 'config/tag_schemes/theme_motif.yaml', 'prompts/tagging/theme_motif.md'),
('literary_entities', '文学描述对象标签', '1.0', '人物、地点、建筑、事件、物件等文学对象', 'config/tag_schemes/literary_entities.yaml', 'prompts/tagging/literary_entities.md');
```

这张表解决：

- 哪些维度存在。
- 每个维度的版本。
- 每个维度用哪个词表。
- 每个维度用哪个 prompt。
- 哪些维度可过滤。
- 哪些维度可向量化。

---

## 4. 新增 `book_tag_results`：多维度打标结果表

这是升级的核心表。

```sql
CREATE TABLE IF NOT EXISTS book_tag_results (
    id INTEGER PRIMARY KEY AUTOINCREMENT,

    book_id INTEGER NOT NULL,
    call_no TEXT,
    title TEXT,

    scheme_code TEXT NOT NULL,
    scheme_version TEXT NOT NULL DEFAULT '1.0',

    tags_json TEXT NOT NULL,

    confidence_score REAL,
    confidence_scores_json TEXT,
    reasoning TEXT,
    evidence_json TEXT,

    llm_model TEXT,
    llm_provider TEXT,
    prompt_version TEXT,

    llm_status TEXT DEFAULT 'pending',
    retry_count INTEGER DEFAULT 0,
    error_message TEXT,

    source TEXT DEFAULT 'llm',
    operator TEXT,

    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,

    UNIQUE(book_id, scheme_code, scheme_version)
);
```

建议索引：

```sql
CREATE INDEX IF NOT EXISTS idx_book_tag_results_book_id
ON book_tag_results(book_id);

CREATE INDEX IF NOT EXISTS idx_book_tag_results_scheme
ON book_tag_results(scheme_code, scheme_version);

CREATE INDEX IF NOT EXISTS idx_book_tag_results_status
ON book_tag_results(llm_status);

CREATE INDEX IF NOT EXISTS idx_book_tag_results_book_scheme_status
ON book_tag_results(book_id, scheme_code, llm_status);

CREATE INDEX IF NOT EXISTS idx_book_tag_results_call_no
ON book_tag_results(call_no);
```

为什么这样设计：

| 字段                     | 作用                           |
| ------------------------ | ------------------------------ |
| `scheme_code`            | 区分阅读体验、主题母题、体裁等 |
| `scheme_version`         | 支持词表或 prompt 升级         |
| `tags_json`              | 保存该方案的完整标签           |
| `confidence_score`       | 方案整体置信度，方便筛选       |
| `confidence_scores_json` | 每个字段的细粒度置信度         |
| `reasoning`              | 推荐解释、人工审核             |
| `evidence_json`          | 标签证据，后续非常有用         |
| `source`                 | 支持 llm、manual、import、rule |
| `operator`               | 记录人工修订者                 |

这样一本书可以有多条标签：

```text
book_id=1001, scheme_code=reading_experience
book_id=1001, scheme_code=genre_form
book_id=1001, scheme_code=theme_motif
book_id=1001, scheme_code=literary_entities
```

## 5. 新增 `book_embedding_records`：向量状态表

当前 `embedding_status` 挂在 `literary_tags` 上，只能表达：

```text
这本书是否完成了一次向量化
```

但未来你需要表达：

```text
这本书的 full_profile_v2 是否完成
这本书的 theme_motif_v1 是否完成
这本书的 literary_entities_v1 是否完成
这本书用哪个 embedding 模型完成
写入了哪个 ChromaDB collection
```

所以应该新增表：

```sql
CREATE TABLE IF NOT EXISTS book_embedding_records (
    id INTEGER PRIMARY KEY AUTOINCREMENT,

    book_id INTEGER NOT NULL,

    embedding_scope TEXT NOT NULL,
    embedding_profile_version TEXT NOT NULL DEFAULT '1.0',

    scheme_code TEXT,
    scheme_version TEXT,

    embedding_model TEXT NOT NULL,
    vector_provider TEXT,
    vector_collection TEXT NOT NULL,
    embedding_id TEXT,

    source_text_hash TEXT,
    source_text_preview TEXT,

    embedding_status TEXT DEFAULT 'pending',
    error_message TEXT,
    retry_count INTEGER DEFAULT 0,

    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    completed_at TEXT,

    UNIQUE(
        book_id,
        embedding_scope,
        embedding_profile_version,
        embedding_model,
        vector_collection
    )
);
```

建议索引：

```sql
CREATE INDEX IF NOT EXISTS idx_book_embedding_records_book_id
ON book_embedding_records(book_id);

CREATE INDEX IF NOT EXISTS idx_book_embedding_records_scope
ON book_embedding_records(embedding_scope, embedding_profile_version);

CREATE INDEX IF NOT EXISTS idx_book_embedding_records_status
ON book_embedding_records(embedding_status);

CREATE INDEX IF NOT EXISTS idx_book_embedding_records_collection
ON book_embedding_records(vector_collection);

CREATE INDEX IF NOT EXISTS idx_book_embedding_records_embedding_id
ON book_embedding_records(embedding_id);
```

推荐的 `embedding_scope`：

| scope                  | 含义                      |
| ---------------------- | ------------------------- |
| `legacy_literary_tags` | 旧版 `literary_tags` 向量 |
| `full_profile`         | 全量图书画像              |
| `reading_experience`   | 阅读体验向量              |
| `theme_motif`          | 主题母题向量              |
| `literary_entities`    | 文学对象向量              |
| `genre_form`           | 体裁文体向量              |
| `summary_only`         | 仅简介向量                |
| `curation_profile`     | 策展画像向量              |

推荐 collection 命名：

```text
literature_full_profile_v1
literature_theme_motif_v1
literature_entities_v1
literature_reading_experience_v1
```

这样你以后可以并存：

```text
full_profile_v1
full_profile_v2
theme_motif_v1
theme_motif_v2
```

方便回滚和 A/B 测试。

## 6. 可选新增 `tag_vocabulary_terms`：标签词表与别名表

如果你希望标签规范化，不想每次只依赖 YAML，可以建表。

```sql
CREATE TABLE IF NOT EXISTS tag_vocabulary_terms (
    id INTEGER PRIMARY KEY AUTOINCREMENT,

    scheme_code TEXT NOT NULL,
    field_name TEXT NOT NULL,

    aliases_json TEXT,
    parent_value TEXT,

    description TEXT,
    is_active INTEGER DEFAULT 1,

    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,

```

索引：

```sql
CREATE INDEX IF NOT EXISTS idx_tag_vocab_scheme_field
ON tag_vocabulary_terms(scheme_code, field_name);

CREATE INDEX IF NOT EXISTS idx_tag_vocab_value
ON tag_vocabulary_terms(canonical_value);
```

用途：

```text
老城、老城区、老街区 -> 旧城

```

如果你短期还不想加复杂度，可以继续用 YAML 做词表，后期再把 YAML 导入这张表。

## 7. 新增 `book_tag_field_index`：可选的标签倒排索引表

SQLite 对 JSON 查询不如专用检索库方便。你现在的 tags 都放在 `tags_json`，如果后续要频繁做：

```text
找 theme_motif.themes 包含“记忆”的书
找 genre_form.primary_genre = “小说”的书
找 literary_entities.object_types 包含“建筑”的书
```

只靠 JSON 文本会很麻烦。

建议增加一张“展开后的标签索引表”。

```sql
CREATE TABLE IF NOT EXISTS book_tag_field_index (
    id INTEGER PRIMARY KEY AUTOINCREMENT,

    book_id INTEGER NOT NULL,

    scheme_code TEXT NOT NULL,
    scheme_version TEXT NOT NULL DEFAULT '1.0',

    field_name TEXT NOT NULL,
    tag_value TEXT NOT NULL,

    tag_value_normalized TEXT,
    confidence_score REAL,

    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,

    UNIQUE(book_id, scheme_code, scheme_version, field_name, tag_value)
);
```

索引：

```sql
CREATE INDEX IF NOT EXISTS idx_book_tag_field_index_book_id
ON book_tag_field_index(book_id);

CREATE INDEX IF NOT EXISTS idx_book_tag_field_index_lookup
ON book_tag_field_index(scheme_code, field_name, tag_value_normalized);

CREATE INDEX IF NOT EXISTS idx_book_tag_field_index_field_value
ON book_tag_field_index(field_name, tag_value_normalized);
```

这张表不是源数据，源数据仍然是 `book_tag_results.tags_json`。

它的作用是：

```text
方便过滤
方便统计
方便 QueryTranslator 结果落到 SQL 查询
方便 Chroma metadata 构造
```

例如：

```sql
SELECT book_id
FROM book_tag_field_index
WHERE scheme_code = 'theme_motif'
  AND field_name = 'themes'
  AND tag_value_normalized IN ('记忆', '成长');
```

我建议中期一定要做这张表。

# 四、推荐历史表升级方案

当前 `literature_recommendation_history` 的问题是：

```text
book_ids 是 JSON/文本
llm_conditions 是 JSON/文本
没有记录候选池
没有记录各路检索分数
没有记录最终排序原因
难以排查“为什么推荐/为什么没推荐”
```

推荐系统后续会越来越复杂，所以历史表应该分成：

```text
recommendation_runs
recommendation_items
```

---

## 1. 新增 `literature_recommendation_runs`

记录一次推荐请求。

```sql
CREATE TABLE IF NOT EXISTS literature_recommendation_runs (
    id INTEGER PRIMARY KEY AUTOINCREMENT,

    request_id TEXT UNIQUE,

    user_input TEXT NOT NULL,
    theme_name TEXT,
    slogan TEXT,
    description TEXT,
    target_vibe TEXT,

    translated_query_json TEXT,
    filter_conditions_json TEXT,
    search_keywords_json TEXT,
    synthetic_query TEXT,

    retrieval_strategy TEXT,
    embedding_scopes_json TEXT,

    use_vector INTEGER DEFAULT 1,
    vector_weight REAL DEFAULT 0.5,
    bm25_weight REAL DEFAULT 0.5,
    randomness REAL DEFAULT 0.2,

    final_theme TEXT,

    status TEXT DEFAULT 'success',
    error_message TEXT,

    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);
```

索引：

```sql
CREATE INDEX IF NOT EXISTS idx_recommendation_runs_user_input
ON literature_recommendation_runs(user_input);

CREATE INDEX IF NOT EXISTS idx_recommendation_runs_created_at
ON literature_recommendation_runs(created_at);

CREATE INDEX IF NOT EXISTS idx_recommendation_runs_theme
ON literature_recommendation_runs(theme_name);
```

---

## 2. 新增 `literature_recommendation_items`

记录每次推荐中的每一本书。

```sql
CREATE TABLE IF NOT EXISTS literature_recommendation_items (
    id INTEGER PRIMARY KEY AUTOINCREMENT,

    run_id INTEGER NOT NULL,
    book_id INTEGER NOT NULL,

    rank INTEGER,
    final_score REAL,

    vector_score REAL,
    bm25_score REAL,
    tag_match_score REAL,
    rerank_score REAL,
    diversity_score REAL,

    source TEXT,
    matched_tags_json TEXT,
    reason TEXT,

    passed_filter INTEGER DEFAULT 1,
    filtered_reason TEXT,

    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,

    UNIQUE(run_id, book_id)
);
```

索引：

```sql
CREATE INDEX IF NOT EXISTS idx_recommendation_items_run_id
ON literature_recommendation_items(run_id);

CREATE INDEX IF NOT EXISTS idx_recommendation_items_book_id
ON literature_recommendation_items(book_id);

CREATE INDEX IF NOT EXISTS idx_recommendation_items_rank
ON literature_recommendation_items(run_id, rank);

CREATE INDEX IF NOT EXISTS idx_recommendation_items_book_recent
ON literature_recommendation_items(book_id, created_at);
```

这样你以后排查问题会非常方便：

```sql
SELECT *
FROM literature_recommendation_items
WHERE book_id = 1234
ORDER BY created_at DESC;
```

可以知道：

```text
这本书是否被召回
由 vector 召回还是 BM25 召回
最终分数多少
是否被二次过滤
是否因为历史去重被排除
```

---

## 3. 保留旧 `literature_recommendation_history`

短期不删除，继续兼容当前 `theme_deduplicator`。

升级策略：

```text
旧逻辑继续写 literature_recommendation_history
新逻辑同时写 recommendation_runs + recommendation_items
验证稳定后，让去重逻辑改读 recommendation_items
最后旧表只读或归档
```

# 六、状态机升级建议

## 1. 打标状态机

当前：

```text
pending
success
failed
```

建议扩展为：

| 状态            | 含义                   |
| --------------- | ---------------------- |
| `pending`       | 待打标                 |
| `processing`    | 正在打标               |
| `success`       | 成功                   |
| `failed`        | 失败，可重试           |
| `skipped`       | 主动跳过，如元数据不足 |
| `invalid`       | LLM 返回格式不合法     |
| `manual_review` | 低置信度，需要人工审核 |

你可以先在 `book_tag_results.llm_status` 支持这些状态，不必改旧表。

---

## 2. 向量状态机

当前：

```text
pending
completed
failed
```

建议扩展为：

| 状态         | 含义                             |
| ------------ | -------------------------------- |
| `pending`    | 待向量化                         |
| `processing` | 正在向量化                       |
| `completed`  | 完成                             |
| `failed`     | 失败                             |
| `stale`      | 源标签或拼接策略变化，向量已过期 |
| `skipped`    | 不需要向量化                     |

其中 `stale` 很重要。

当以下内容变化时，应该标记旧向量为 `stale`：

```text
tags_json 变化
scheme_version 变化
embedding_profile_version 变化
embedding_model 变化
```

# 十、是否要加外键？

SQLite 可以加外键，但我建议谨慎。

理论上可以：

```sql
FOREIGN KEY(book_id) REFERENCES books(id)
```

但你当前系统里：

- `books` 由外部模块拥有。
- 文学模块用 `sqlite3.connect` 直连。
- SQLite 默认外键未必开启。
- 历史数据可能不干净。
- 迁移时外键容易阻碍导入。

所以我的建议是：

## 第一阶段不强制外键

用索引和 JOIN 保证性能，用业务逻辑保证一致性。

## 第二阶段增加一致性检查脚本

例如：

```sql
SELECT btr.book_id
FROM book_tag_results btr
LEFT JOIN books b ON btr.book_id = b.id
WHERE b.id IS NULL;
```

## 第三阶段如果数据稳定，再考虑外键

这比一开始强加外键更稳。

# 十一、是否要使用 SQLite JSON1？

如果运行环境的 SQLite 支持 JSON1，可以用：

```sql
json_extract(tags_json, '$.themes')
```

但我不建议核心逻辑依赖它。

原因：

- Python 环境自带 SQLite 版本不一定一致。
- JSON 数组查询复杂。
- 标签过滤会越来越多，JSON 查询性能不可控。

更好的方式是：

```text
tags_json 作为源数据
book_tag_field_index 作为查询索引
```

这是更稳的工程方案。
